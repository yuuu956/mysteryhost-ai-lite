# Product Requirements Document: MysteryHost AI Lite

## 1. Product Overview

MysteryHost AI Lite 是一个文字版 AI 剧本杀主持人原型项目。

它模拟剧本杀主持人的核心职责，包括案件背景展示、角色分配、分轮线索释放、玩家提问回应和最终推理复盘。

本项目的目标不是简单生成故事，而是探索 AI 如何在互动推理游戏中承担一个有规则、有边界、有流程控制能力的功能型角色。

## 2. Product Positioning

MysteryHost AI Lite 是一个面向轻量推理游戏场景的 AI 主持人 Demo。

产品定位：

> 用 AI 扮演剧本杀主持人，帮助玩家完成单人文字推理体验，并展示 AI 在游戏流程管理、信息控制和推理反馈中的应用能力。

## 3. Target Users

### 3.1 推理游戏爱好者

这类用户喜欢剧本杀、密室逃脱、悬疑故事和解谜游戏，希望获得低门槛的推理体验。

### 3.2 AI 产品学习者

这类用户希望通过一个可运行的 Demo 理解 LLM、Prompt、状态管理、Agent Workflow 和 AI 评测等概念。

### 3.3 AI 产品经理面试展示场景

该项目可作为 AI 产品经理作品集项目，用于展示 AI 产品设计、功能拆解、交互设计和风险控制能力。

## 4. User Pain Points

传统剧本杀体验存在以下问题：

1. 需要主持人组织流程，单人难以体验完整游戏。
2. 剧本杀流程复杂，需要管理角色、线索、时间线和真相。
3. 玩家推理后缺少结构化复盘反馈。
4. 传统聊天机器人容易剧透，无法稳定控制游戏阶段。
5. AI 生成故事容易发散，需要产品机制限制输出边界。

## 5. Product Goals

MysteryHost AI Lite 的 MVP 目标包括：

1. 搭建一个可运行的文字版 AI 剧本杀主持人原型。
2. 展示案件背景、角色卡和线索释放流程。
3. 支持玩家向主持人提问。
4. 支持玩家提交最终推理并获得复盘反馈。
5. 通过本地 mock 数据先验证核心产品流程。
6. 为后续接入 LLM API、Prompt 设计和 Agent Workflow 打基础。

## 6. MVP Scope

### 6.1 Included Features

| Feature     | Description                       |
| ----------- | --------------------------------- |
| 案件背景展示      | 展示案件标题、主题、死者信息、案发地点和核心谜题          |
| 角色卡展示       | 展示角色身份、公开信息、隐藏秘密和可疑点              |
| 线索释放        | 按 Round 1、Round 2、Round 3 分阶段释放线索 |
| 主持人问答       | 玩家输入问题后，主持人根据当前信息进行不剧透回应          |
| 推理复盘        | 玩家提交最终推理后，系统根据关键词和证据进行评分与反馈       |
| GitHub 文档沉淀 | 输出 README、学习路线、PRD 和学习笔记          |

### 6.2 Excluded Features

MVP 暂不包含：

1. 多人实时联机
2. 用户登录
3. 数据库
4. 真实 LLM API 接入
5. 语音主持人
6. 图片生成
7. 完整 RAG 知识库

这些能力将在后续版本中扩展。

## 7. Core User Flow

```text
用户进入页面
→ 查看案件背景
→ 阅读角色卡
→ 查看第一轮线索
→ 向 AI 主持人提问
→ 释放下一轮线索
→ 继续推理
→ 提交最终推理
→ 获得复盘评分和真相说明
```

## 8. Functional Requirements

### 8.1 案件背景模块

用户需要看到：

* 剧本标题
* 剧本主题
* 玩家人数
* 难度
* 死者信息
* 案发地点
* 核心谜题

该模块帮助用户快速建立推理背景。

### 8.2 角色卡模块

每个角色卡需要包含：

* 角色名
* 身份
* 公开信息
* 隐藏秘密
* 与死者关系
* 可疑点

该模块用于制造人物关系和推理空间。

### 8.3 线索释放模块

线索按照回合释放：

* Round 1：现场线索
* Round 2：人物关系线索
* Round 3：关键反转线索

该模块用于控制游戏节奏，避免玩家一开始获得全部信息。

### 8.4 主持人问答模块

玩家可以输入问题，主持人需要：

* 基于当前游戏信息回答
* 避免提前透露凶手
* 提醒玩家关注线索矛盾
* 在信息不足时拒绝直接判断

当前 MVP 使用本地规则逻辑模拟 AI 主持人。

### 8.5 推理复盘模块

玩家提交最终推理后，系统需要输出：

* 推理评分
* 推理等级
* 命中情况
* 遗漏点
* 最终真相说明

当前 MVP 使用关键词匹配方式模拟复盘判断。

## 9. AI Capability Mapping

| AI Capability      | Current MVP Implementation | Future Upgrade                    |
| ------------------ | -------------------------- | --------------------------------- |
| LLM                | 暂未接入，使用本地规则模拟              | 接入 API 生成动态回应                     |
| Prompt Engineering | 文档阶段设计                     | 编写剧本生成、问答、复盘 Prompt               |
| Structured Output  | 角色卡、线索卡、复盘卡                | 要求 LLM 输出 JSON                    |
| Memory             | 使用 currentRound 和消息记录      | 增加完整 game state                   |
| Agent Workflow     | 手动流程控制                     | 主持人 Agent 自动判断下一步                 |
| Tool Use           | 本地函数模拟                     | 模拟 releaseClue、reviewReasoning 工具 |
| Risk Control       | 本地规则防剧透                    | Prompt 约束 + 输出校验                  |

## 10. Success Metrics

### 10.1 Product Metrics

* 用户是否能理解案件背景
* 用户是否能完成至少一次线索释放
* 用户是否能完成至少一次主持人提问
* 用户是否能提交最终推理
* 用户是否能理解复盘反馈

### 10.2 AI Experience Metrics

* 主持人回答是否不剧透
* 主持人回答是否和当前线索一致
* 复盘结果是否有解释性
* 推理评分是否符合用户直觉
* 输出内容是否结构化、可读

### 10.3 Portfolio Metrics

* GitHub README 是否完整
* 项目是否可运行
* 文档是否能体现 AI 产品经理思维
* commit 记录是否清晰
* 项目是否适合面试讲解

## 11. Risks and Constraints

### 11.1 Spoiler Risk

AI 主持人可能提前泄露最终凶手或真相。

控制方式：

* 限制主持人只基于当前回合信息回答
* 对“凶手”“真相”等问题使用拒答或引导策略

### 11.2 Hallucination Risk

AI 可能编造不存在的线索。

控制方式：

* 使用固定剧本数据作为事实来源
* 后续接入 LLM 时要求基于给定上下文回答

### 11.3 Consistency Risk

生成的角色、线索和真相可能不一致。

控制方式：

* 使用结构化数据管理案件
* 后续加入一致性检查机制

### 11.4 User Experience Risk

如果信息过多，用户可能难以推理。

控制方式：

* 分轮释放线索
* 使用卡片化展示
* 在复盘中明确遗漏点和关键证据
