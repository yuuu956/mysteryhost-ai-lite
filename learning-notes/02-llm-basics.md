# 02 LLM Basics

本笔记用于记录我对大语言模型 LLM 的基础理解，并结合 MysteryHost AI Lite 项目分析 LLM 在 AI 产品中的实际作用。

## 1. 什么是 LLM？

LLM，全称 Large Language Model，即大语言模型。

从产品经理视角看，LLM 可以理解为一种能够理解和生成自然语言的 AI 能力。它可以根据用户输入、上下文信息和任务要求，生成回答、总结内容、改写文本、提取结构化信息或完成推理辅助。

在 AI 产品中，LLM 通常不是单独存在的，而是和 Prompt、数据、工具、业务流程、权限控制和评测体系结合使用。

## 2. LLM 在产品中的常见能力

LLM 常见能力包括：

1. 文本生成
   例如生成故事、文案、邮件、报告、对话。

2. 文本理解
   例如理解用户问题、识别意图、总结内容。

3. 信息抽取
   例如从文本中提取姓名、时间、地点、事件、标签。

4. 结构化输出
   例如按照 JSON、表格、卡片格式输出结果。

5. 多轮对话
   例如根据上下文持续回答用户问题。

6. 推理辅助
   例如分析原因、比较方案、生成建议。

7. 风格迁移
   例如把文本改写成正式、轻松、悬疑、游戏化等风格。

在 MysteryHost AI Lite 中，LLM 可以用于：

* 生成案件背景
* 生成角色设定
* 生成线索
* 扮演 AI 主持人回答玩家问题
* 分析玩家最终推理
* 输出推理复盘报告

## 3. Token

Token 是大模型处理文本的基本单位。

一个 token 不一定等于一个字或一个单词。中文、英文、标点、空格都会被模型切分成不同 token。

从产品经理视角看，token 主要影响三个问题：

1. 成本
   模型调用通常按照输入 token 和输出 token 计费。

2. 上下文长度
   模型一次能记住和处理的内容有限，不能无限塞入信息。

3. 响应速度
   输入越长、输出越长，通常响应越慢。

在 MysteryHost AI Lite 中，如果后续接入 LLM API，需要控制传给模型的内容：

* 当前案件背景
* 已释放线索
* 当前回合
* 玩家问题
* 主持人回答规则

不应该每次都把所有无关内容全部传入，否则会增加成本和延迟。

## 4. Context Window

Context Window 指模型一次对话中可以处理的上下文范围。

如果上下文过长，模型可能无法完整理解，或者系统需要截断部分内容。

在 AI 产品设计中，Context Window 会影响：

* 对话历史保留多少
* 文档内容如何切分
* 当前任务需要哪些上下文
* 哪些信息需要进入 Prompt
* 哪些信息应该通过 RAG 或数据库检索

在 MysteryHost AI Lite 中，主持人回答玩家问题时，不需要知道所有未来真相，只需要知道：

* 当前回合
* 已释放线索
* 案件基础设定
* 玩家当前问题
* 防剧透规则

这就是一种上下文控制。

## 5. Temperature

Temperature 是影响模型输出随机性的参数。

一般来说：

* Temperature 越低，输出越稳定、保守、确定。
* Temperature 越高，输出越有创意，但也更容易发散。

从产品角度看，不同场景应该使用不同 temperature。

| 场景         | 建议倾向           |
| ---------- | -------------- |
| 客服问答       | 低 temperature  |
| 法律/医疗/财务辅助 | 低 temperature  |
| 文案创意       | 中高 temperature |
| 故事生成       | 中高 temperature |
| 结构化抽取      | 低 temperature  |
| 游戏剧情生成     | 中等 temperature |

在 MysteryHost AI Lite 中：

* 生成剧本时，可以使用较高 temperature，提高创意。
* 主持人问答时，应使用较低 temperature，避免乱编线索。
* 推理复盘时，应使用较低 temperature，保证评价稳定。

## 6. Hallucination

Hallucination，即 AI 幻觉，指模型生成了看似合理但实际不存在或不准确的信息。

在 AI 产品中，幻觉是非常重要的风险。

在 MysteryHost AI Lite 中，幻觉可能表现为：

* AI 编造不存在的线索
* AI 提前泄露凶手
* AI 修改既定剧情
* AI 错误判断玩家推理
* AI 给出和当前回合不一致的回答

控制方式包括：

1. 明确事实来源
   让模型只能基于当前案件数据、已释放线索和角色卡回答。

2. 设计 Prompt 约束
   明确告诉 AI 不得编造新线索，不得提前透露真相。

3. 使用结构化数据
   将案件、角色、线索、真相拆成明确字段，减少模型自由发挥空间。

4. 设置拒答机制
   如果玩家问“谁是凶手”，主持人应拒绝直接回答，并引导玩家继续推理。

5. 输出校验
   检查模型回答是否包含未释放线索或最终真相。

## 7. LLM 不是产品本身

一个常见误区是：接入 LLM 就等于完成 AI 产品。

实际上，LLM 只是能力层，真正的 AI 产品还需要：

* 明确用户场景
* 设计输入方式
* 设计输出格式
* 管理上下文
* 控制风险
* 设计交互流程
* 评估效果
* 控制成本和延迟

MysteryHost AI Lite 的核心不是让 AI 随便生成悬疑故事，而是让 AI 在一个有规则的推理游戏中承担主持人角色。

因此，产品设计重点包括：

* 游戏阶段控制
* 线索释放节奏
* 主持人回答边界
* 角色信息权限
* 推理复盘逻辑
* 防剧透机制

## 8. LLM 在 MysteryHost AI Lite 中的功能规划

### 8.1 当前 MVP

当前版本暂未接入真实 LLM API，而是使用本地 mock 数据和规则逻辑模拟 AI 功能。

当前实现包括：

* 本地案件数据
* 本地角色卡
* 本地线索释放
* 本地规则版主持人问答
* 本地规则版推理复盘

这样做的原因是：

* 一天内可以快速完成 MVP
* 降低接口配置和成本问题
* 先验证产品流程是否成立
* 后续再逐步接入 LLM

### 8.2 后续 LLM 增强版

后续可以让 LLM 负责：

1. 生成案件背景
   根据主题、人数、难度生成剧本基础设定。

2. 生成角色卡
   输出角色名、身份、动机、秘密和可疑点。

3. 生成线索
   按回合生成现场线索、人物关系线索和关键反转线索。

4. 主持人问答
   根据当前回合、已释放线索和玩家问题，生成不剧透的回答。

5. 推理复盘
   根据玩家推理和最终真相，分析命中点、遗漏点和推理质量。

## 9. AI 产品经理需要关注的 LLM 问题

在设计 LLM 产品时，AI 产品经理需要关注：

1. 模型适合解决这个问题吗？
2. 用户输入是否足够清晰？
3. 模型需要哪些上下文？
4. 输出格式是否可控？
5. 如何避免模型胡说？
6. 如何避免成本过高？
7. 如何减少响应延迟？
8. 用户如何判断 AI 输出是否可信？
9. AI 出错时产品如何兜底？
10. 哪些步骤需要人工确认？

## 10. 阶段性总结

LLM 是 AI 产品的重要能力基础，但它不是完整产品。

AI 产品经理需要做的是：

> 将 LLM 的语言理解和生成能力，放入具体用户场景中，通过 Prompt、数据、交互、状态管理和风险控制，把不稳定的模型能力转化为相对可控、可用、可评估的产品体验。

在 MysteryHost AI Lite 中，LLM 的价值不是简单生成故事，而是帮助构建一个能管理剧情、控制线索、回应玩家、避免剧透并完成推理复盘的 AI 主持人系统。
